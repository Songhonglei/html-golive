# OpenGoLive 境内外宣传计划

制定日期：2026-11-07。适用于 OpenGoLive（安装包和仓库名称 `html-golive`）的首轮推广，执行期为北京时间 2026-11-07 至 2026-11-20。按一名维护者、14 天、现金预算人民币 0 至 2000 元安排；费用和指标均为规划值，不代表报价或传播效果承诺。

先通过开发者社区和自托管社区获得真实试用，再用部署案例争取技术媒体报道，最后接触综合科技媒体。首轮以“用户成功发布第一个页面”为主要成果，GitHub Star 作为辅助指标。

## 产品定位与受众

统一对外名称为 **OpenGoLive（html-golive）**，同时保留准确的安装包名、CLI 和仓库链接，减少搜索时的名称混淆。

中文介绍：**把 HTML 报告、看板和小工具发布到自己的电脑、NAS 或内网服务器，通过链接分享。**

英文介绍：**OpenGoLive turns HTML reports, dashboards, and small tools into shareable sites on your own infrastructure.**

宣传重点是发布与管理环节。AI 生成 HTML 是一个使用场景；OpenGoLive 本身不负责生成页面，也不是模型推理服务。

| 受众 | 具体问题 | 演示内容 | 期望行动 |
| --- | --- | --- | --- |
| 使用 AI 编程工具的个人开发者 | 生成了 HTML，却只能发送附件或录屏 | 从一份生成好的 HTML 到可访问的页面 | 安装并发布一个示例 |
| 企业内部的数据、产品和研发团队 | 报告和原型需要在团队内查看、更新 | 内网发布、更新页面、管理权限 | 申请参与一次部署访谈 |
| NAS 和自托管用户 | 希望集中托管个人页面与小工具 | 自有服务器上的页面管理和持久化数据 | 按教程部署并反馈环境 |
| Python 和开源开发者 | 想评估轻量部署工具的实现与扩展性 | CLI、可切换后端、恢复机制与测试证据 | 试用、提交可复现问题或贡献 |

每篇内容只讲一个场景。首篇以“HTML 文件变成可分享页面”为主；数据库、身份认证和协作作为后续深度内容。

## 发布状态与宣传口径

本轮统一推广和分发版本为 **0.9.8**，覆盖 PyPI、GitHub Release、随包 Agent Skill、中英文文档与项目介绍页。SkillHub 和 ClawHub 按各平台实际发布与审核状态逐项核验。

发布制品安装与升级复验在第 1 至 2 天完成。对外使用“0.9.8 已发布”的表述前，确认对应平台确实提供正确文件；若某个 Skill 平台仍在审核，直接说明该平台状态并提供 GitHub Release 的同版本 Skill 包。发布与验收范围见[版本交付说明](release-0.9.8.md)。

宣传表述遵循以下边界：

- 链接能否被他人访问取决于部署网络。`localhost` 只供本机访问，内网地址要求网络可达；公网分享需要另行配置服务器、域名或接入方式。
- “自己的基础设施”是部署选择。外部字体、页面资源、远程后端和身份服务是否联网，应按实际配置说明，避免笼统承诺完全离线。
- 安全扫描描述为“发布前的规则检测”，不宣称覆盖所有凭证或阻止所有恶意页面。
- 0.9.8 的条件编辑冲突保护目前限定于 macOS/Linux 本地存储；S3、Supabase 存储的编辑保存返回不支持，不能宣传为所有存储上的完整协作编辑。见[协作文档](collaboration.md)。
- P3 的共享状态验证范围为同主机本地磁盘；WebDAV 的公网验证对应指定服务和账号。跨主机高可用、所有 NAS、所有生产身份提供商不作为现有验收结论。见[阶段总结](stage-summary-0.9.8.md)。

## X 专项宣传计划

X 列为 P1，从准备期持续到两周结束。重点触达 AI 编程工具用户、独立开发者、Python 开发者和自托管爱好者。英文作为主语言，有中文受众的已有账号可另发中文摘要，避免把两种语言挤进同一条帖子。

优先使用维护者已有账号，以开发者身份展示产品和回答问题；是否另建项目账号取决于已有受众和后续维护能力。简介写清 OpenGoLive 与 `html-golive` 的对应关系，主页链接指向仓库或已验证可访问的项目介绍页。置顶一条介绍帖，包含具体用途、简短演示和安装入口。

| 阶段 | 内容 | 行动目标 |
| --- | --- | --- |
| 准备期 | 展示“HTML 做好了，怎样交给同事看”的问题和页面成果；征集部署环境反馈 | 了解需求，找到愿意试用的人 |
| 第 3 天 | 一条英文介绍帖，附约 30 至 45 秒字幕录屏，展示文件、命令和浏览器结果 | 让读者理解用途并进入安装说明 |
| 第 4 至 7 天 | 两至三条不同角度的短帖：内网报告、页面更新、安装常见问题；适合时组织为短串帖 | 降低试用难度，收集问题 |
| 第 8 至 10 天 | 一条开发取舍串帖和一条演示；在确实相关时链接英文教程或 Show HN 讨论 | 建立技术可信度，回应开发者疑问 |
| 第 11 至 14 天 | 发布三至四条真实案例、修复过程或实用技巧；案例需先取得用户授权 | 带来持续试用和外部推荐 |

两周以 8 至 12 条原创内容为起点，一条串帖作为一个内容单元，不把回复拆成发帖数量目标。复用主录屏制作短版，在现有 25 至 35 小时总投入中预留约 4 至 6 小时，用减少次要平台同步的方式安排。

每条内容采用“具体问题、实际结果、一个行动入口”的结构。先展示页面成果，再解释发布方式。主帖可直接放仓库链接，不预设“外链必须放评论”等算法结论；后续根据自身数据调整。话题标签按需选用一至两个，如 `#OpenSource` 或 `#SelfHosted`。

可使用下面的英文介绍作为维护者审核后的初稿，配已发布功能的真实演示：

> Built an HTML report with AI? Share it on your own infrastructure. OpenGoLive publishes HTML files as sites on your computer, NAS, or intranet server. Open source. Try it: https://github.com/Songhonglei/html-golive

该文案中的链接以实际部署网络可达为前提。所有帖子以正式分发的 0.9.8 功能和对应验证结果为准。

互动优先围绕真实的部署问题：人工查找 self-hosted HTML、share HTML report、intranet dashboard 等相关讨论，有具体经验时再回复。先回应对方的问题，介绍项目时披露维护者身份；只在与内容确实相关时提及作者或社区账号。X 禁止虚假互动和垃圾信息，执行时避免批量重复回复、无关提及和互赞互转安排。[X 真实性政策](https://help.x.com/en/rules-and-policies/authenticity)

初期可分别测试北京时间 09:00 至 11:00、21:00 至 23:00 两个窗口，选择维护者能及时答疑的时段；这些是排期假设，不是最佳发布时间结论。第 7 天结合受众地区与实际反馈调整。

单独记录每条内容的主题、发布时间、链接、可获得的展示和点击数据，以及自报来自 X 的成功部署反馈。X 的分析面板和字段取决于账号实际权限，先核对可用项，不为完成计划默认购买订阅。[官方分析面板说明](https://business.x.com/help/tweet-activity-dashboard)

落地页具备分析支持时，链接使用 `utm_source=x`、`utm_medium=social`，沿用本计划的 campaign。两周争取 3 至 5 位来自 X 的用户成功发布页面，计入整体 10 至 20 位试用目标；粉丝数和曝光仅作辅助观察。未接入统计时，通过公开问题、GitHub 流量及自愿反馈做有限归因。X 两周新增广告预算为零。

建议主选题：

1. 中文入门稿：《AI 生成了一个 HTML 页面，怎样把它交给同事使用》。以公开版实测为基础，逐步展示网络访问条件。
2. 自托管稿：《在自己的服务器上管理 HTML 报告和小工具》。以安装和更新流程为主，不预先声称已兼容所有 NAS。
3. 技术深度稿：《轻量发布工具如何处理恢复身份与编辑冲突》。使用 0.9.8 的源码和对应验证结果，解释取舍。
4. 英文入门稿：*From an HTML file to a self-hosted report your team can open*。按英文读者重新组织场景和术语。
5. 真实案例稿：完成至少一次外部部署访谈后再写；性能、节省时间和用户规模均采用实测或授权数据。

对比内容围绕部署成本、网络环境、管理功能和适用边界展开。Nginx、GitHub Pages、Netlify、Vercel 可作为读者熟悉的参照，但应按当时版本和配置验证差异，不写未经测量的性能优越结论。

## 成效指标与归因

以下为首轮检验目标，不是历史数据或流量预测。准备期先记录基线，第 7 天按实际访问量和答疑能力调整，第 14 天复盘。

| 指标 | 两周检验目标 | 统计方法 |
| --- | --- | --- |
| 场景内容 | 2 篇中文、1 篇英文、1 条主演示 | 记录公开链接与版本 |
| X 持续传播 | 8 至 12 条原创内容，争取 3 至 5 位成功部署用户 | 按账号可用数据和自愿反馈统计；部署用户计入整体试用目标 |
| 定向投递 | 8 至 12 个有效渠道 | 有提交记录或公开帖子，不把同文镜像重复计数 |
| 真实试用 | 10 至 20 位外部用户完成第一个页面发布 | 自愿提供部署反馈或参加访谈 |
| 持续使用 | 首批成功用户中至少 5 人在一周后仍使用 | 自愿回访，记录样本量 |
| 用户案例 | 2 至 3 份可复现或经用户授权的案例 | 环境、步骤、结果齐备 |
| 外部引用或收录 | 争取 2 至 4 处 | 区分目录收录、转载、独立报道与付费内容 |
| GitHub 关注 | 记录净增 Star、外部 Issue 和贡献者 | 与启动前基线比较，不单独作为成功判据 |

渠道链接可使用 `utm_source`、`utm_medium` 和 `utm_campaign`，例如 `utm_campaign=opengolive_launch_202611`。只有落地页具备统计支持时，UTM 才能形成归因；当前是否已接入分析需另行确认。没有分析工具时，用各平台后台、GitHub 仓库流量和反馈中的自报来源做有限归因，不宣称精确转化率。

PyPI 下载包含自动化下载和重复安装，不能直接当作用户数。自托管实例的活跃情况优先通过自愿反馈了解，不为宣传默认加入产品遥测。

若一个渠道带来至少 3 位完成发布的用户或一份深入部署反馈，可追加同主题内容；若访问充足但安装频繁失败，优先修复安装与文档；若投递缺少回应，调整选题和案例后再决定是否继续。
